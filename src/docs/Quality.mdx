              ))}
            </tbody>
          </table>
        </div>
      ))}
    </>
  )

## Como medimos

### Stack de teste

| Camada | Ferramenta | Versão |
|---|---|---|
| Runner | [`vitest`](https://vitest.dev) | ^3 |
| Ambiente DOM | [`jsdom`](https://github.com/jsdom/jsdom) | ^25 |
| Render & query | [`@testing-library/react`](https://testing-library.com/react) + `@testing-library/jest-dom` | 16.x / 6.x |
| Eventos do usuário | [`@testing-library/user-event`](https://testing-library.com/docs/user-event/intro/) | 14.x |
| Cobertura | `@vitest/coverage-v8` (provider `v8` nativo do Node) | ^3 |

A configuração vive em `vitest.config.ts` e o setup global em `vitest.setup.ts`.

### Provider de cobertura

Usamos **v8 coverage** (não Istanbul) porque ele instrumenta diretamente o motor JS — sem transformação extra do código, sem mismatch entre o que roda em produção e o que é medido. As métricas são:

- **Lines** — linhas executadas / linhas executáveis
- **Statements** — sentenças JS distintas executadas
- **Functions** — declarações de função executadas pelo menos uma vez
- **Branches** — ramos lógicos (`if`/`else`, `&&`, `||`, ternário, `switch`, `??`) percorridos

Arquivos excluídos da cobertura (em `vitest.config.ts`):

```ts
exclude: ["src/**/*.stories.tsx", "src/**/*.test.tsx", "src/docs/**", "src/index.ts"]
```

### Princípios (F.I.R.S.T.)

Os testes seguem F.I.R.S.T.:

- **Fast** — cada `*.test.tsx` roda em milissegundos. Total abaixo de 1 minuto mesmo com 346 testes.
- **Independent** — sem ordem implícita; cada `it()` é isolado via Testing Library `cleanup()`.
- **Repeatable** — sem `Date.now()` real, sem rede, sem timers vazando. `vitest.config.ts` define `dangerouslyIgnoreUnhandledErrors: true` apenas para absorver o vazamento conhecido do `input-otp` (timer pós-teardown da lib externa).
- **Self-validating** — passa ou falha, sem inspeção manual de logs.
- **Timely** — testes são commitados junto com o componente. Quando o componente é reescrito, o teste é reescrito também.

### Classes de teste cobertas

Cada componente recebe ao menos cinco classes:

| Classe | Pergunta que responde | Exemplos |
|---|---|---|
| **Renderização** | "Monta sem crash com props mínimas?" | `expect(getByRole(...)).toBeInTheDocument()` |
| **API pública** | "Cada prop documentada produz efeito observável?" | `aria-invalid` aparece com `error` setado; `disabled` bloqueia clique |
| **Interação** | "Eventos do usuário disparam os callbacks corretos?" | `userEvent.click` → `expect(onClick).toHaveBeenCalled()` |
| **Acessibilidade** | "Roles, labels e estados ARIA estão corretos?" | `aria-checked="mixed"` em indeterminate; `role="alert"` em error |
| **Edge cases** | "Empty / disabled / long-content / controlled ↔ uncontrolled quebram?" | empty arrays, max-length pasteado, indeterminate state |

### O que NÃO testamos (e por quê)

- **CSS visual / pixel-perfect** — Storybook + revisão humana cobrem isso melhor.
- **Layout responsivo** — jsdom não calcula layout. Visual regression em browser real fica para uma futura camada com Playwright.
- **Implementação interna** — testes asseram comportamento observável, não tipos de hook, não classes intermediárias.

### Strict mode & double-render

`React.StrictMode` está **desligado nos testes** para evitar duplo-render acidental no jsdom. Componentes que dependem de hidratação SSR são testados separadamente quando aplicável.

### Stubs do jsdom

Em `vitest.setup.ts` polyfilamos APIs que o jsdom não implementa nativamente:

- `window.matchMedia` — usado por `useIsMobile` e Sidebar
- `ResizeObserver` — usado por cmdk, recharts
- `IntersectionObserver` — usado por Image/Video lazy loading
- `Element.prototype.scrollIntoView` — usado por cmdk
- `URL.createObjectURL` / `revokeObjectURL` — usado por FileUpload thumbnails

## Comandos

```bash
bun run test              # roda tudo uma vez
bun run test:watch        # modo watch
bun run test:coverage     # gera coverage/ + lcov + html
bun run sync:coverage     # test:coverage + atualiza src/docs/_coverage.ts
```

Após `test:coverage`, abra `coverage/index.html` no navegador para drilldown linha-a-linha.
