# Qualidade & Testes

A lib é coberta por **três camadas complementares** de teste, cada uma exercitando o código em um nível diferente:

1. **Unit + integration tests** — `vitest` + `jsdom` + `@testing-library/react`. Foco em lógica, ARIA, eventos sintéticos.
2. **Storybook test runner** — Playwright/Chromium roda **todas as stories** em browser real para smoke-test de renderização + `play` functions com asserções.
3. **End-to-end specs** — Playwright em browser real contra a Storybook viva. Foco em flows que precisam de viewport, portais, hover real, focus trap.

Esta página agrega métricas dessas três camadas. Os números são auto-sincronizados de:
- `coverage/coverage-summary.json` (vitest com provider v8) → `src/docs/_coverage.ts`
- `tests/e2e/*.spec.ts` + `src/**/*.stories.tsx` → `src/docs/_e2e-stats.ts`

```bash
bun run sync:coverage     # roda test:coverage + atualiza _coverage.ts
bun run sync:e2e-stats    # recalcula _e2e-stats.ts
```

## Como medimos — visão geral

### Camadas de teste

| Camada | Ferramenta | Roda em | O que cobre |
|---|---|---|---|
| **Unit** | vitest + jsdom + @testing-library/react | DOM simulado | Lógica, ARIA, eventos sintéticos, controlled state, validação de props |
| **Storybook test runner** | @storybook/test-runner (Playwright internamente) | Chromium real, headless | Smoke render de todas as stories + `play` functions com asserções |
| **E2E** | @playwright/test | Chromium real | Focus trap, hover, drag-and-drop, layout responsivo, atalho de teclado em browser |

### Stack detalhada

| Camada | Ferramenta | Versão |
|---|---|---|
| Runner unit | [`vitest`](https://vitest.dev) | ^3 |
| Ambiente DOM | [`jsdom`](https://github.com/jsdom/jsdom) | ^25 |
| Render & query | [`@testing-library/react`](https://testing-library.com/react) | 16.x |
| Cobertura | `@vitest/coverage-v8` | ^3 |
| E2E runner | [`@playwright/test`](https://playwright.dev) | ^1.60 |
| Storybook runner | [`@storybook/test-runner`](https://storybook.js.org/docs/writing-tests/test-runner) | ^0.24 |
| Asserções em play fn | [`@storybook/test`](https://storybook.js.org/docs/writing-tests/component-testing) | ^8.6 |
| Browser | Chromium 1223 (bundled) | — |

Configs:
- `vitest.config.ts` — runner unit + coverage exclude
- `vitest.setup.ts` — polyfills do jsdom (matchMedia, ResizeObserver, IntersectionObserver, scrollIntoView, URL.createObjectURL)
- `playwright.config.ts` — projeto Chromium + webServer auto-start do storybook em modo dev
- `.storybook/test-runner.ts` — hooks placeholder para futuras checagens a11y/visuais

### Provider de cobertura (v8 vs Istanbul)

Usamos **v8** porque ele instrumenta diretamente o motor JS — sem transformação extra do código, sem mismatch entre o que roda em produção e o que é medido. As métricas:

- **Lines** — linhas executadas / linhas executáveis
- **Statements** — sentenças JS distintas executadas
- **Functions** — declarações de função executadas pelo menos uma vez
- **Branches** — ramos lógicos (`if/else`, `&&`, `||`, ternário, `switch`, `??`) percorridos

Arquivos excluídos da cobertura (em `vitest.config.ts`):

```ts
exclude: ["src/**/*.stories.tsx", "src/**/*.test.tsx", "src/docs/**", "src/index.ts"]
```

> **Importante:** o Playwright E2E **não contribui para a porcentagem de coverage** acima. v8 instrumenta apenas o processo do vitest. Os E2E garantem que a UI compõe corretamente em Chromium real, mas o número de coverage cobre só a parte exercitada por unit/integration tests.

### Princípios (F.I.R.S.T.)

- **Fast** — vitest abaixo de 1 min com 346 testes; Storybook test runner ~ 42 s para 289 stories; E2E ~30 s para 29 specs em paralelo.
- **Independent** — sem ordem implícita; cada `it()` / `test()` é isolado.
- **Repeatable** — sem `Date.now()` real, sem rede, sem timers vazando entre testes.
- **Self-validating** — passa ou falha, sem inspeção manual de logs.
- **Timely** — testes commitados junto com o componente.

### Classes de teste cobertas

| Classe | Pergunta que responde | Onde mora |
|---|---|---|
| **Renderização** | "Monta sem crash com props mínimas?" | vitest unit / storybook smoke |
| **API pública** | "Cada prop documentada produz efeito observável?" | vitest unit |
| **Interação** | "Eventos do usuário disparam os callbacks corretos?" | vitest unit + storybook `play` |
| **Acessibilidade** | "Roles, labels e estados ARIA corretos?" | vitest unit |
| **Edge cases** | "Empty / disabled / long-content / controlled ↔ uncontrolled quebram?" | vitest unit |
| **Focus trap** | "Tab cicla só dentro do modal?" | Playwright E2E |
| **Hover real** | "Tooltip aparece com hover + delay e some no mouse-leave?" | Playwright E2E |
| **Portal interaction** | "Conteúdo portaled acessível via roles globais?" | Playwright E2E |

### O que NÃO testamos

- **Browsers não-Chromium** — todas as camadas (vitest jsdom, Storybook test-runner, Playwright) rodam em Chromium. WebKit/Firefox não estão no CI; rodadas manuais quando necessário.
- **Render server-side (SSR/RSC)** — a lib é client-only (`"use client"` nos componentes interativos). Nenhum teste exercita Next.js RSC.
- **Implementação interna** — testes asseram comportamento, não tipo de hook, não classes intermediárias.

> **Visual regression JÁ está coberta:** `tests/e2e/visual.spec.ts` mantém 57 baselines via `toHaveScreenshot` (Google Fonts bloqueado em cada teste para determinismo). Layout responsivo é coberto em E2E pelos projects `mobile-chromium` (Pixel 5) e `tablet-chromium` (iPad gen 7).

### Stubs do jsdom

Em `vitest.setup.ts` polyfilamos APIs que o jsdom não implementa nativamente:

- `window.matchMedia` — usado por `useIsMobile` e Sidebar
- `ResizeObserver` — usado por cmdk
- `IntersectionObserver` — usado por Image/Video lazy loading
- `Element.prototype.scrollIntoView` — usado por cmdk
- `URL.createObjectURL` / `revokeObjectURL` — usado por FileUpload thumbnails

> Em browser real (Storybook/Playwright) essas APIs existem nativas, então **alguns bugs só pegam em uma das camadas**.

## Comandos

```bash
# Unit (vitest)
bun run test                # roda tudo uma vez
bun run test:watch          # modo watch
bun run test:coverage       # gera coverage/ + lcov + html

# Storybook test runner (precisa do storybook rodando em :6006)
bun run storybook           # em outro terminal
bun run test:storybook      # roda todas as stories como Playwright tests
bun run test:storybook:ci   # constrói storybook estático + serve + roda — para CI

bun run test:e2e            # CI mode (auto-starts Storybook dev)
bun run test:e2e:headed     # mostra o browser
bun run test:e2e:ui         # Playwright UI mode

# Sync de stats para a página Quality
bun run sync:coverage       # roda test:coverage + atualiza _coverage.ts
bun run sync:e2e-stats      # recalcula _e2e-stats.ts
```

Após `test:coverage`, abra `coverage/index.html` para drilldown linha-a-linha.
Após `test:e2e`, abra `playwright-report/index.html` para o relatório HTML com traces/screenshots.

## Layout responsivo

A camada de **testes responsivos** vive em `tests/e2e/responsive.spec.ts` e roda no project `chromium` mudando o viewport em runtime via `page.setViewportSize()`. Diferente dos projects `mobile-chromium` e `tablet-chromium` (que pegam o componente em um único viewport fixo), `responsive.spec.ts` exercita a mesma story em mobile/tablet/desktop e valida que o componente **adapta** o layout.

| Viewport | Width × Height | Uso |
|---|---|---|
| Mobile  | 375 × 667 | smartphone retrato |
| Tablet  | 768 × 1024 | iPad retrato |
| Desktop | 1280 × 720 | notebook padrão |

### O que validamos

| Componente | Comportamento responsivo testado |
|---|---|
| **Sidebar** | Mobile→`<Sheet>` overlay; Desktop→`<aside>` persistente |
| **DataTable** | Container `overflow-x: auto` em qualquer viewport |
| **Tabs** | Trigger list não estoura largura da viewport |
| **Dialog** | Conteúdo respeita width disponível, não vira minúsculo |
| **Image** | `aspectRatio` mantém proporção (16:9 stays 16:9) |
| **FieldShell** | Label position adapta layout (flex-col em narrow) |

### Comando

```bash
bun run test:e2e -- tests/e2e/responsive.spec.ts
```

Para visual diff em múltiplos viewports da mesma story, use o project-level testing:

```bash
bun run test:e2e:mobile     # roda mobile.spec.ts no Pixel 5
bun run test:e2e:tablet     # roda tablet.spec.ts no iPad
bun run test:visual         # 57 baselines em desktop
```

### Limitação conhecida

A maioria dos componentes da lib **não tem media queries internas** — eles são "intrinsicamente responsivos" porque usam `w-full`, `flex-wrap`, `min-w-0`, etc. Sidebar é a exceção (usa `useIsMobile`). Por isso a maior parte dos testes responsivos valida **invariantes geométricas** (não estourar largura, manter aspect ratio) e não "elementos mudam ao cruzar breakpoints".
